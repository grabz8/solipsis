\section{Solipsis Protocol Details}


\subsection{Data Structures Maintained at Node}
Solipsis nodes maintain a set of data structures to manage the
interaction with the objects that constitute the 3D world. In the
following, we describe each of these structures for site nodes and for
avatar nodes, respectively.

\subsubsection{Site Nodes}
\label{sec:sinodes}

\paragraph{Visible List}
The visible list, \vlist, is a map of object identifiers to object
descriptors. It contains an entry for each object ) that is visible
from the current site node's cell. Each element in the visible list
may be a site or an avatar and may be inside or outside of the current
node's cell. A more fine grained distinction is provided by the
\emph{visible site list}, the \emph{avatar list}

\paragraph{}
\paragraph{RayNet}
Site nodes have access to a \rn object that provides them with two
functions.
\begin{itemize}
\item 
$\gn()$: may be called by a site node and return the list of the node's
neighbors. 
\item 
$\route(m, p)$: may be called by both avatars and site nodes and routes a
message $m$ to the site node associated with the location $p$ in the
coordinate space. 
\end{itemize}

as reactions to unexpected disconnections or network failures.

\subsubsection{Protocol Messages}
Protocol Messages are exchanged asynchronously between Solipsis nodes
using UDP. This is true even when the two communicating nodes (e.g. a
site and an avatar) actually reside on the same peer. As above, each
message may be classified according to the type of its recipient:
site, or avatar.

Periodically, site nodes inform the avatars in their cells as well as
neighboring site nodes about visible objects. This is achieved through
the combination of two mechanisms. First, site nodes send a \vupdate
message every $T_v$ seconds to neighboring sites and avatars. This
message contains copies of the descriptors of all the objects visible
from the site node's cell. Second, every $T_c$, where $T_c<< T_v$,
site nodes send a \cupdate message to inform neighboring sites and
visiting avatars about changes occurred from the last \vupdate
message. The \cupdate message also consists of a list of node
descriptors. However, while the absence of a descriptor from a
\vupdate message implies that the corresponding object is no longer
within visibility, its absence from a \cupdate message simply implies
that the object's descriptor has not changed since the last update.
\inlinedf{Updates to neighboring sites nodes may be sent
  directly. Updates to avatars however might be sent using some kind
  of multicast tree.}

\begin{algorithm}
\caption{site node receiving an \adesc message}
\begin{algorithmic}
\Procedure{sendViewUpdate}{}{Executed every $T_v$ seconds by each site
node.}
\State \vupdate.\sn=\cursn++
\State \vupdate.\descs=\vlist
\ForAll {$n$ \in \rn.\gn}
  \State send \vupdate to $n$
\EndFor
\ForAll {$d$ \in \olist}
  \State send \vupdate to $d.\UID$
\EndFor
\EndProcedure

\Procedure{sendChangedUpdate}{}{Executed every $T_c$ seconds by each site
node.}
\State \cupdate.\sn=\cursn++
\State \cupdate.\descs=\clist
\State $\clist=\emptyset$
\ForAll {$n$ \in \rn.\gn}
  \State send \cupdate to $n$
\EndFor
\ForAll {$d$ \in \olist}
  \State send \cupdate to $d.\UID$
\EndFor
\EndProcedure

\end{algorithmic}
\end{algorithm}
